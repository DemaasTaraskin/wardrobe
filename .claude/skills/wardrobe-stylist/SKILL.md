# Wardrobe Stylist

Скил делает три вещи из чата: **push** (каталог и фото → Supabase), **looks** (собрать луки и
записать их), **feedback** (выгрузить оценки и журнал «надел»). Схема данных и все решения —
в [DATA.md](../../../DATA.md); этот файл — про то, как ими пользоваться.

Луки собираю **я, в чате**. Скрипты только проверяют состав по правилам и пишут в базу:
в приложении вызовов Claude нет.

## Что где лежит

| Что | Где |
|---|---|
| Ключи проекта | `clothes/.env` — `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` |
| Сессия входа | `clothes/.supabase-session.json` (в `.gitignore`, обновляется сама) |
| Каталог вещей | `clothes/wardrobe.json` — 97 карточек, источник для push |
| Оригиналы фото | `C:\Users\manyl\wardrobe-photos\` — не копировать в проект |
| Эталон стиля | `clothes/reference_look.md` |
| Внешность и посадка | `clothes/profile.md` — локально, в базу не идёт |

Скрипты запускаются из корня `clothes/`:
`python .claude/skills/wardrobe-stylist/scripts/<скрипт>.py`. Нужен только Python с Pillow,
остальное — стандартная библиотека.

## Приватность

- `service_role` не нужен и в проекте не хранится. Всё идёт под пользователем: publishable-ключ
  плюс сессия, полученная по коду на почту.
- Пароли не участвуют нигде. Код из письма пользователь присылает в чат, скрипт меняет его на сессию.
- Фото, каталог, `profile.md`, `.env`, `feedback.md` — только локально. В git уходит код,
  миграция и этот скил.
- Каждая строка в базе принадлежит своему пользователю (RLS). Второй пользователь на этапе 7
  заводит свою сессию — строки не пересекаются.

## 1. Вход

```
python .claude/skills/wardrobe-stylist/scripts/login.py request <почта>
python .claude/skills/wardrobe-stylist/scripts/login.py verify <код из письма>
python .claude/skills/wardrobe-stylist/scripts/login.py accept <ссылка или адрес из строки браузера>
python .claude/skills/wardrobe-stylist/scripts/login.py status
```

`request` шлёт письмо (аккаунт должен быть заведён приглашением в панели Supabase —
самостоятельная регистрация выключена). Дальше сессия обновляется сама, повторный вход нужен редко.

Три вещи, на которых тут легко споткнуться:

- **В письме может не быть кода.** Шаблоны Supabase по умолчанию содержат только ссылку.
  Тогда: либо `accept <адрес ссылки>` (не открывая её), либо открыть ссылку и передать
  `accept <адрес из строки браузера>` — страница не откроется, но в адресе будет
  `#access_token=…`, и это уже готовая сессия. Чтобы в письмах появились шесть цифр,
  добавь строку `<p>Код: {{ .Token }}</p>` в шаблоны **Confirm signup** и **Magic Link**
  (Authentication → Emails).
- **Ссылки одноразовые**, и новый запрос гасит токен из прошлого письма. Работаем всегда
  с самым свежим письмом.
- **Встроенная почта Supabase — 2 письма в час.** Упёрлись в `over_email_send_rate_limit` —
  ждём начала следующего часа, а не шлём ещё раз.

## 2. `wardrobe push` — каталог и фото в базу

```
python .claude/skills/wardrobe-stylist/scripts/push.py --dry-run   # посмотреть, что будет
python .claude/skills/wardrobe-stylist/scripts/push.py             # залить
python .claude/skills/wardrobe-stylist/scripts/push.py --limit 3   # пробный прогон
```

- Вещь узнаётся по `source_file` — повторный запуск правит карточку, а не создаёт вторую.
- Фото сжимается до 800 px по длинной стороне в WebP с прозрачностью и кладётся в приватный
  бакет по пути `{user_id}/items/{item_id}.webp`. Сжатые копии кэшируются в `.webp-cache/`.
- Незменившиеся фото повторно не заливаются (`--photos all` — перезалить всё, `--photos skip` —
  только карточки).
- В конце: сколько добавлено и обновлено, какие фото остались без карточки и наоборот.

**Заливка фото — внешнее действие: спрашивай подтверждение перед первым полным прогоном.**

Правки карточек, сделанные в приложении, push перезапишет из `wardrobe.json`. Если пользователь
правил что-то на телефоне — сначала выгрузи текущее состояние
(`items_export.py --json wardrobe.json`) или внеси правку в `wardrobe.json` руками.

## 3. `wardrobe looks <сезон>` — собрать луки

Порядок работы:

1. `python .claude/skills/wardrobe-stylist/scripts/items_export.py` — активные вещи из базы
   (`--slot base`, `--situation office` — фильтры). Это источник правды, а не `wardrobe.json`:
   пользователь мог поправить карточки в приложении.
2. Прочитать `reference_look.md` и `profile.md`.
3. Собрать луки: **5 ситуаций × 3 банда (+5…+10, +10…+15, +15…+20) × 2–3 варианта**, всего 30–45.
   В каждой ячейке стараться дать хотя бы один лук с рукавами — он и будет дождевым.
4. Записать их в файл вида `looks_batch1.json` (формат — в шапке `looks_push.py`), вещи указывать
   по `source_file`.
5. `python .claude/skills/wardrobe-stylist/scripts/looks_push.py looks_batch1.json --dry-run`,
   починить ошибки, затем запустить без `--dry-run`.
6. `python .claude/skills/wardrobe-stylist/scripts/looks_push.py --coverage` — таблица покрытия.

Что проверяет скрипт (ошибка — не запишет, заметка — просто предупредит):

- обязательные слоты `base`, `bottom`, `shoes`; `outer` обязателен, если верх банда ≤ +15;
- вещь стоит в слоте, который у неё разрешён, и годится для этой ситуации;
- температурный диапазон вещи пересекается с бандом (не закрывает целиком — заметка);
- диапазоны формальности всех вещей пересекаются; с формальности 3 логотипов быть не должно;
- не больше одного рисунка (принт, полоска, клетка) на лук; больше двух небазовых цветов — заметка;
- аксессуаров не больше двух, одна вещь не стоит в двух слотах;
- `rain_ok` считается сам: в луке есть рукава (хоть один слой не `sleeveless`).

Ячейки, где хорошего лука не собрать, идут в `gaps` — с текстом, чего именно не хватило
(«на +10…+15 в дождь нет непромокаемой куртки»). Пустая ячейка без записи в `gaps` — это
недоделанная работа, а не результат.

Стиль: опираться на `reference_look.md` и `profile.md`, контраст давать фактурами, а не цветами,
«почему работает» писать в 1–3 предложения человеческим языком — это то, что читается на экране лука.

Вторая партия после отзывов: `looks_batch2.json` с `"batch": 2` и флагом `--retire-existing`
(прежние активные луки уйдут в `retired`, оценки на них останутся).

## 4. `wardrobe feedback` — что показали две недели

```
python .claude/skills/wardrobe-stylist/scripts/feedback.py
```

Считает долю ❤️, частые причины 👎, собирает комментарии, журнал «надел», ячейки и две важные
цифры: вещи, не попавшие ни в один лук, и вещи, которые в луках есть, но ни разу не надеты.
Подробности пишутся в `feedback.md` (локально, в `.gitignore`).

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `Нет сохранённой сессии` | войти заново (раздел 1) |
| `Signups not allowed` при `request` | пользователь не заведён: панель Supabase → Authentication → Users → Add user → Send invitation |
| `Could not find the table 'public.items'` | миграция `supabase/001_init.sql` не выполнена в SQL Editor |
| `new row violates row-level security` | сессия чужая или `user_id` не проставлен — проверить `login.py status` |
| `duplicate key … items_source_file_uniq` | в `wardrobe.json` две карточки с одинаковым `source_file` |
| Проект Supabase «paused» | бесплатный проект засыпает после недели простоя: разбудить в панели, проверить автопинг в GitHub Actions |
